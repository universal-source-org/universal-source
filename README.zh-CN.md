# Universal Source

**面向多运行时、多平台的可移植内容源互操作规范。**

[English](./README.md)

Universal Source 是一个开放项目，目标是探索一套统一契约，让内容源的描述与执行不再绑定某一个 App、某一种运行时或某一类设备生态。

今天，很多“源”高度依赖宿主应用：它们调用私有 JavaScript API、使用应用专属的 JSON 结构、依赖隐式运行时行为，甚至依赖没有正式文档的约定。结果是，同一份源很难跨客户端复用，每一个应用都逐渐形成自己的兼容性孤岛。

Universal Source 想让真正可移植的对象变成 **Source 本身**。

## 我们想实现什么

一个 Universal Source 应当描述的是 **“这个源需要完成什么”**，而不是规定 **“必须由哪一种技术来执行”**。具体执行工作交给符合规范的 Runtime。

目前项目遵循以下设计原则：

- **可移植** —— 一份源不应该只属于某一个 App。
- **运行时无关** —— JavaScript、Rust、Go、Swift、Kotlin 或其他实现，都应该能够遵守同一份契约。
- **尊重既有生态** —— 已经存在的大量源不能被忽略；迁移与兼容本身就是核心问题。
- **基于能力声明** —— Source 明确声明自己需要什么能力，而不是默认宿主一定提供某套私有环境。
- **可验证** —— 兼容性应该通过真实世界的源样本验证，而不只是写在文档里。
- **核心尽量小，边界允许扩展** —— 稳定最小公共契约，把变化留给能力扩展，避免核心规范频繁破坏兼容性。

## 我们正在解决的问题

一个典型的内容源可能需要：

1. 提供元数据；
2. 搜索；
3. 列表或发现内容；
4. 解析详情；
5. 解析最终可用资源；
6. 发起网络请求；
7. 解析结构化或非结构化响应；
8. 保存少量状态；
9. 在必要时执行受控脚本。

不同应用通常会用完全不同的方式描述这些行为。即使两个生态都使用 JavaScript 或 JSON，它们的 API 往往仍然互不兼容。

Universal Source 尝试定义这样一层公共边界：

```text
Source Definition
      ↓
Universal Source Contract
      ↓
Conforming Runtime
      ↓
App / TV / Mobile / Desktop / Server
```

我们的目标不是要求所有实现都使用同一种语言，而是要求它们对同一份 Source 呈现一致、可验证的行为。

## 当前状态

Universal Source 目前处于 **早期设计阶段**。

规范、执行模型、能力系统、兼容策略以及真实世界样本集都仍在设计中。在第一个稳定版本之前，API 与术语都可能发生明显变化。

这个仓库将作为项目公开工作的主要入口。

## 初始范围

第一阶段重点关注：

- Source 元数据与 Manifest；
- 请求 / 响应基础能力；
- 搜索与发现；
- 详情与资源解析；
- Runtime 能力与权限；
- 可预测的错误语义；
- 对既有 JavaScript / JSON 源格式的兼容；
- 真实世界兼容性样本集。

随着设计逐渐清晰，我们也会明确记录哪些问题 **不属于** Universal Source 的职责范围。

## 一个标准必须用兼容性证明自己

规范只有在不同实现能够得到一致行为时才有价值。

因此，Universal Source 希望把真实世界兼容性直接纳入标准形成过程：

```text
existing sources
      ↓
compatibility corpus
      ↓
conformance tests
      ↓
multiple runtimes
      ↓
same observable behavior
```

长期目标可以概括为一句话：

> 定义一次，在任意技术栈实现，让 Source 跨生态运行。

## 仓库方向

在项目还处于早期阶段时，本仓库会先承载核心设计工作。等边界真正稳定以后，再根据实际需要拆分规范、Conformance Suite、Runtime、SDK 与工具链。

我们不会为了“看起来像一个大项目”而提前制造大量空仓库。

## 参与项目

现在恰恰是这个项目最需要质疑和反例的阶段。

如果你做过内容源系统、解析器、插件运行时、媒体客户端、抓取基础设施、沙箱执行环境或跨平台 SDK，我们尤其欢迎真实兼容案例和工程层面的讨论。

在增加任何一个新抽象之前，我们希望先回答三个问题：

1. 它解决了什么真实世界问题？
2. 不同 Runtime 能否一致地实现它？
3. 现有 Source 能否以合理成本迁移过来？

## 名称

**Universal Source** 表达的是项目真正想建立的边界：一种不依附于单一宿主应用、能够跨实现长期存在的 Source 格式与执行契约。

---

Universal Source 目前仍是实验性项目，尚不宣称规范稳定、生产可用或已经实现完整兼容。
