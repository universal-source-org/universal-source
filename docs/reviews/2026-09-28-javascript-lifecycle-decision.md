# JavaScript invocation lifecycle decision

Status: **design decision incorporated into proposed RFC 0001; not accepted or implemented**. Baseline: `f4029bf64f74ea8ee94cf0fba2c8cd0d5985a016`. Phase 3 remains active. No engine selected, no engine ADR, no production change.

## Decision and authority

Choose **lifecycle Model B: a fresh execution realm for every executing invocation**, destroyed on every outcome. This label is independent of RFC 0001's unchanged **return Model B**, the complete Source API envelope. Mutable JavaScript state persistence between calls is **removed from the proposal**, not optional, conditional or an engine optimization. A logical loaded instance remains reusable after ordinary outcomes; it retains the immutable package snapshot, declarations, host configuration and serialization/lifecycle state, never source JavaScript values.

The [Source API](../../spec/source-api.md) defines independent operations and portable data. [Lifecycle §3](../../spec/lifecycle.md#3-invoke-an-operation) explicitly requires IDs to work without a particular call order, serializes calls, and separates transient memory from host-managed persistent storage. Section 4 does not require unloading a healthy logical instance after ordinary failure. Neither document promises persistent JavaScript module environments; initialization was explicitly left to a future binding. That promise appeared only in the unaccepted RFC. Resetting each call therefore changes the proposal, not the completed normative/static baseline. Call-order independence alone would not prohibit a cache; the decision removes persistence because its convenience does not justify reaction-graph machinery unnecessary to these operations.

For `let cache = new Map()` at module scope, each call starts with a new Map. It can cache computation across helpers/awaits within that call, never across independent operations, even two synchronous successful calls. Host storage/cookies may persist only under their separately defined permission, namespace and future service profiles; realm destruction neither supplies nor erases them. Sources cannot use those services during initialization. No storage API is introduced here.

It does not repeat an engine survey or assert universal engine impossibility.

The engine-specific sources/revisions and API boundaries remain in those reviews. This decision infers a portable lifetime policy from demonstrated destruction/isolation primitives; it does **not** claim the complete revised binding has been demonstrated. In particular, a context handle being dropped is not by itself proof that jobs, native roots or provider resolvers cannot still reach its objects.

## Models A–E

For comparison, **safe async quiescence** would mean that no surviving source job, reaction, continuation, resolver or host completion from the old call can ever execute source code or use its capability scope, including after any future source action. An empty runnable queue, a settled returned Promise, or zero outstanding service requests proves none of this. An unresolved Promise with no reachable resolver/reaction can be harmless; distinguishing it from a retained future source of execution requires more than counting pending Promises.

| Model | State and Promise-graph consequence | Feasibility and disposition |
| --- | --- | --- |
| A: persistent realm, full revocation | Guarantees mutable state. Already queued and future reactions must be suppressed, including missing handlers, child settlement, await and species work. Retained child/async Promises remain visible later, so leaving them pending versus rejecting/fulfilling them is a new observable contract. New B-owned reactions on an old Promise must be distinguished from A-owned ones. | Requires pre-effect ownership and suppression throughout engine Promise machinery, plus a specified abandoned-graph state. Reviewed public APIs do not supply it. A fork/private extension or new upstream mechanism could help, but neither its cost nor source benefit is justified here. Reject for this binding. |
| B: fresh realm each call | No cross-call mutable state. Entire old graph loses every source observer; pending children/awaits remain in their last states until released, with no synthetic settlement. Queued and future jobs cannot enter a later realm. | Explicit single-job scheduling and an isolated, destructible execution domain are realistic embedding primitives already partly demonstrated. Avoids Promise-graph introspection and callback substitution. Select, subject to complete embedding proof before acceptance. |
| C: reuse only after proven async quiescence | State persists only following proof. Until then queued work could change children, run custom resolvers, request services or generate more jobs; unresolved graphs can be dormant yet resumable later. | A bounded drain is not proof; an unbounded drain is unacceptable and delays a ready result behind unrelated work. Ordinary public job APIs cannot certify the strong property above. A universal conservative proof that always discards reduces to B. Reject as a portable persistence rule. |
| D: source MUST leave no residual async work | To retain state, the runtime must distinguish harmless inert Promises from reachable unresolved chains, await resumptions and service settlements. Violations would require detection before another call. | Author discipline cannot enforce authority/lifetime isolation. Async functions and implicit await bypass ordinary `.then` instrumentation; ordinary unresolved values are not intrinsically violations. No reliable detector or justified new error classification is available. Reject rather than create an unenforceable MUST. |
| E: reuse unless async safety is ambiguous | Persistence is conditional on an engine's proof. Purely synchronous return does not imply safety: a call can register a reaction or start a service and return immediately. Fully settled returned work need not settle sibling/nested work. | A conservative implementation can always discard, but differing proofs make observable cache/counter/prototype survival engine-dependent. Declaring persistence non-portable burdens authors/tests without a necessary Source API benefit. Requiring reset observability and allowing only unobservable immutable caches reduces to B. Reject opportunistic mutable reuse. |

A, C, D and E are not viable portable choices on current evidence; they remain alternatives, not implementation modes. This decision need not assign fictional cancellation semantics to their unresolved graphs to make them viable. A would require a new explicit graph policy; C/D/E require a detector or restriction not established by the experiments. B is the only selected model, with all Promise states specified below.

| Decision criterion | Why B is preferred; cost retained |
| --- | --- |
| Portability and enforceability | Whole-domain isolation/destruction replaces selective reaction revocation; no engine-private API becomes normative. A complete implementation still has to prove roots/queue disposal. |
| Determinism and conformance | Every call resets, independent of GC, engine analysis, return style or queue shape. Controlled job order and terminal gates are directly testable. External completion arrival remains host-dependent. |
| Isolation and host capability lifetime | An old JavaScript graph cannot be reached by a new call. Host revocation independently closes late native completion paths. |
| Source API requirements | Independent IDs, full envelopes, exactly-one outcome and serialized calls remain. Logical instance reuse is preserved without mutable realm reuse. |
| Implementation complexity | Creates/evaluates/destroys realms repeatedly; avoids graph liveness certification, token propagation through implicit await, and abandoned-child semantics visible to another call. |
| Author ergonomics and caching | Authors use ordinary Promise/await semantics within a call and need not prove background quiescence. Cross-call module caches are lost; await required effects/results. Immutable package/parsed-code caching is permitted without mutable source objects. |
| Performance | Reinitialization costs CPU/allocation and counts toward deadlines/limits. No benchmark or speed claim justifies relaxing reset. Persistent host storage is not an implicit cache workaround. |

## Loading, invocation and instance health

The [revised RFC](../../spec/rfcs/0001-javascript-execution-binding.md#4-initialization-state-and-disposal) distinguishes a **logical loaded instance** from its **execution realms**:

1. Validate manifest, grants/services and the complete immutable module graph. Evaluate synchronous initialization in a disposable load-validation realm, capturing direct operation declarations at instantiation and checking their identity after evaluation. Failure remains a load diagnostic (A1); no ready instance or operation envelope. Dispose this realm before readiness, without executing any source Promise job. This preserves discovery of initialization faults at loading.
2. Serialize an admitted ready call, checking declaration/input and pre-execution interruption/limits before creating its execution realm. No source executes for an undeclared operation or invalid input. Create a fresh realm, reinstantiate and synchronously reevaluate the same snapshot, capture/check fresh operation functions, copy input and inject a fresh invocation context. The load probe's objects/functions never survive. No file reread, lazy graph discovery or new initialization export is added.
3. Per-call initialization uses the same synchronous/no-capability rule. An ordinary throw, forbidden initialization job or changed export identity now occurs within a ready call: sanitized `SOURCE_ERROR`, no operation body called, realm discarded. Checked resource limits and observed cancellation/deadline retain their existing codes and conservative instance disposal. An initial successful probe cannot exempt later allocation/evaluation from checks. This is the only new ready-error mapping needed by repeated setup.
4. Execute and reach the boundary below; destroy the realm on success, returned failure, invalid result or exception alike. A healthy logical instance returns to Ready with its snapshot, not its JavaScript memory. Execution cancellation/deadline/resource termination conservatively disposes the logical instance as in the earlier proposal; waiting calls cannot execute and use deferred U1 host reporting. Merely queued cancellation/expiry or checked pre-execution rejection leaves the active call/healthy instance intact. Reinitialization is execution for this rule.

Mutable realm pooling is forbidden even for purely synchronous calls. Immutable source/parsed-code caches may be shared only if they cannot expose a module environment, function, intrinsic, engine handle or other mutable JavaScript value. Ordinary failure requires neither package reload nor revalidation; logical instance disposal requires both. Explicit host unload also revokes active work and waits for source quiescence. This does not change static Phase 2 reuse.

## Terminal boundary and Promise states

Keep candidate detection at the **next source-job boundary** after synchronous return or observed intrinsic-Promise settlement; the exported call must have unwound. Jobs run to completion subject to cooperative interruption. Settlement in the middle of a running job does not interrupt that job or allow a second call; if it loops afterward, a deadline can still win. No ordinary `.then` observer may add a turn. Compare an alternative “drain all allowed work first”: it admits sibling effects after the requested result, can grow without bound, and still cannot certify dormant graphs. Therefore readiness does not wait for unrelated work to settle.

At that boundary, before any next source job:

1. Close source-job and service-delivery gates and revoke the invocation's capabilities. On observed interruption without a candidate, close those gates and revoke authority at observation, then reach cooperative source quiescence before retirement/publication; do not report destruction while code can run.
2. Copy/validate the candidate or classify failure under bounded non-executing host processing. Preserve current grants, the classification of already produced same-scope host rejections, error precedence limits and interruption checks; no getter, observer, rejection handler or cleanup callback executes.
3. Abandon the **entire** realm graph and queue. Release/neutralize every source-executable root, resolver, provider handle and native completion route. Pending host work is cancelled or detached; teardown invokes no JavaScript, including `finally`, species resolvers or synthetic Promise rejections. Physical memory reclamation may be deferred only if reentry/observability is impossible.
4. Check cancellation/deadline immediately before selecting and publishing exactly one host-owned envelope. Selection is final only here, not an irrevocable success chosen before cleanup. The invocation is complete when source quiescence, revocation and realm retirement are established and the envelope is published; serialization covers all of this. Later cancellation cannot revise it.

Cleanup must be bounded host work under documented structural/resource/checkpoint policies and must not wait for detached I/O to finish. This is not a hard real-time destruction guarantee. An unsafe execution context disposes the logical instance; fatal failures unable to run recovery still have the RFC's existing delivery limitation. No source callback is used to implement cleanup. There is no final job drain, no automatic retry, and no promise that an unawaited external effect completed or was undone.

In the following table, A and B are consecutive invocations, not lifecycle model names.

| Value/work at the terminal boundary | Within A's remaining lifetime | What a later call B can observe |
| --- | --- | --- |
| Unresolved source-created Promise | Remains pending until its storage is released; no artificial fulfillment/rejection. It does not keep the invocation alive. | No reference; B has new module/global memory. |
| Fulfilled/rejected Promise with queued reactions | Settlement is not rewritten. Unstarted jobs are discarded without invoking handlers or child resolvers. | Neither the Promise nor an old reaction runs in B. |
| Reaction on unresolved upstream, not yet queued | Abandoned with the upstream/resolver graph. A late host completion does not even invoke the old JS resolver. | No old reaction can later be enqueued into B. |
| `.then` child, including missing handlers and custom species | Keeps its last settled/pending state until unreachable/released; no replacement return/error, resolver or species work during cleanup. | No observable “cancelled child,” fabricated undefined value or injected rejection. |
| Async-function result Promise | Ordinary ECMAScript behavior before the boundary; abandoned in its last state afterward. | No async result handle crosses the JSON boundary. |
| Nested await continuation / source `finally` | May run in normal FIFO execution before terminal readiness; any remaining continuation is abandoned, not unwound through source cleanup. | No resumption or finally side effect in a later call. |
| Host-service Promise/resolver | Existing settlement is left alone; pending settlement delivery is revoked and native work cancelled/detached. | Neither an old wrapper nor a late resolver acquires B's authority. Completed external effects may still exist. |
| Promise/context retained in module/global memory | Entire memory is abandoned, including inert load-probe Promises. No per-Promise liveness proof is needed. | B starts from freshly evaluated declarations. No stale source reference is representable through JSON-only input/output or storage. |
| Returned pending Promise and empty job queue | **Not yet terminal**: continue host waiting with finite deadline/cancellation checks; do not destroy merely because the queue is empty. | B cannot execute until A terminates and its realm is retired. |

The table is abandonment of an unobservable graph, not ECMAScript Promise cancellation. Jobs queued earlier may run while the operation result is still pending. Ordinary language assimilation, handler propagation and await semantics are preserved during allowed execution; the host does not substitute callback results. B cannot register new reactions on A's old Promise because there is no route to obtain it. That removes the particularly difficult old/new-reaction distinction exercised by Boa without pretending to implement it.

## Capabilities, compatibility and retained constraints

Realm destruction is part of capability revocation but not its only mechanism. Provider scopes require an unforgeable active/liveness check; stop delivery before copying/teardown. Native completions carrying a dead scope perform no new action, settlement or source callback, even if an external request finishes after B begins. Discard obsolete handles rather than rebind them or reject into B with a new brand. Method extraction changes neither authority nor lifetime. No cross-call wrapper can survive via module state under this model; no new service methods are specified. Completed external effects and authorized persistent storage remain governed separately.

RFC edits are confined to §1–2 per-realm instantiation wording; §4 initialization/state/disposal; §5 terminal/job lifetime; §6 realm identity wording; §7 per-call initialization errors and scope wording; §8 wrappers; §9–10 state/isolation wording; compatibility, future conformance, alternatives and internal review. Return Model B, graph restrictions, named exports, JSON-only structural transfer, ordinary error mappings, globals/dynamic compilation restrictions and explicit capability injection remain. A1/U1/U2/P1/D1/D2 are not closed or reprioritized.

The versioning conclusion remains **experimental v0.1 completion, no proposed bump**. This is an incompatible revision of the earlier unaccepted RFC's persistence guarantee, explicitly reported as such; an experimental implementation of that draft must change and identify its revision. No existing normative JavaScript execution guarantee or implemented declarative expectation changes. Acceptance still requires coordinated normative documents and conformance; this review is not acceptance.

## Engine implications and next unit

F1 is resolved **as a proposed lifecycle choice**, not by proving full reaction revocation possible. Per-reaction registration ownership/graph surgery is no longer required between invocations. Ordinary FIFO single-job control is necessary but not alone sufficient: direct settlement observation, bounded non-executing copying, cooperative interruption, complete execution-domain retirement and native completion gating remain mandatory. Realm may mean a whole engine runtime/context pair if queues or roots are runtime-wide; merely creating another global object in a live shared domain is not enough.

QuickJS-NG becomes a credible path to review using a separate rquickjs Runtime/Context pair for each validation/call realm; existing tests cover some disposal/isolation primitives. Boa's custom executor/context offers a path to whole-queue abandonment without callback substitution, but native GC roots, context lifetime, drop behavior and job reachability still need focused evidence. Neither engine is selected, neither is now declared compliant. The original F1 counterexamples remain valid evidence against the old persistent-state proposal.

**Next: review and minimally prove the revised fresh-realm lifecycle through the existing QuickJS-NG/rquickjs embedding path**, without production integration. Trace all roots/jobs/resolvers through load-probe disposal, call completion and interrupted teardown; demonstrate that a late host completion cannot reenter any retired realm and that the next call resets all mutable state. Review feasibility of repeated module instantiation and capture-before-evaluation against public APIs, without implementing a production loader. This is a focused lifecycle proof, not another engine survey or engine choice. If retirement or initialization cannot meet the revised contract, return that specific issue to the RFC before implementation.

Engine selection still needs the remaining evaluation findings resolved: complete module/preflight and export-capture support, exact allowlist and code-generation hardening, non-executing branded/Proxy-safe inspection, exception confidentiality, allocation/CPU/native-work limits, build/licensing and actual target-platform evidence. A successful lifecycle proof alone does not accept the RFC or authorize production execution. Validation and delivery are recorded in the [completed plan](../plans/completed/2026-09-28-javascript-lifecycle-decision.md).
