# Consolidated Phase 3 engine feasibility and selection readiness

Date: 2026-09-29. Reviewed baseline: `3c3ffa4780f09e0597e7318abe2d81941457f6ac`.

**Outcome A — continue QuickJS toward selection.** QuickJS-NG remains the strongest evidenced candidate for this project's restricted, fresh-runtime JavaScript profile. A narrowly maintained async-termination patch and permanent RegExp admission policy are defensible costs. Neither is free; both require explicit ownership and upgrade gates. JSC, V8 and Boa offer worthwhile strengths, but none currently establishes a better complete path across the charter's platforms and RFC semantics.

**Engine selection is not yet justified.** This is a recommendation, not an engine ADR, fork authorization or commitment to integrate QuickJS. The exact next task is the [integrated resource/failure closure spike](#exact-next-task). Module/path containment, complete parser/preflight strategy, platform evidence and patch governance also remain pre-selection gates. Calling the next spike the last necessary experiment would hide those gaps.

RFC 0001 remains proposed and unimplemented. No engine or parser is selected; no engine ADR exists. Production `runtime/` remains the declarative reference runtime. All QuickJS-NG/rquickjs code is experimental. No historical review, dependency, pin, contract or production file changes in this unit. Historical outcomes retain their original scope; later evidence qualifies their implications rather than rewriting them.

Second, the C async harness proves propagation with the patch, while the Rust admission/value/lifecycle suites still use the unmodified engine. Their conjunction needs an integrated proof before selection. Neither caution warrants editing the historical evidence.

## Carrying the async-termination patch

### Bounded surface, substantive ownership

The actual candidate is roughly 40 added lines in one translation unit, with 12 edits across 11 functions. The complete 36-site classification and regression matrix are more valuable than its line count. Conversion guards mostly reuse upstream cleanup, but the void async-generator helper required two callers to propagate pending exceptions. The intermediate UNRESOLVED result demonstrated why a mechanically applied guard is insufficient.

The [existing driver](../../experiments/quickjs-async-termination-fix-spike/build_and_run.py) verifies the original file hash, checks replacement counts and tests baseline/patched engines with sanitizers and leak-abort. Low affected-site churn between pinned 0.16.2 and inspected 0.17.0 makes initial rebasing plausible, not future maintenance predictable. The read-only refresh at [upstream revision `2f0aa72`](https://github.com/quickjs-ng/quickjs/blob/2f0aa72a6b09cf69ff06399bcf9f4c083ac1a278/quickjs.c) still finds all 12 original patch anchors unchanged. No upstream remedy was found. [The existing issue](https://github.com/bellard/quickjs/issues/341) corroborates known Promise/async behavior and caller-propagation concerns; it is not a QuickJS-NG acceptance commitment.

This is a **small maintained compatibility patch with continuing engine-semantic responsibility**, rather than a plan to maintain a new JavaScript engine. The boundary holds only if the project owns this narrow stop-propagation invariant, keeps the RFC profile closed, and continues tracking upstream. It must understand cleanup/refcounts, async-generator states and every new exception-to-rejection path; outsourced line merging is insufficient. Changing GC, compiler architecture, Promise semantics generally, or accumulating unrelated engine fixes would cross into de facto engine maintenance and trigger reconsideration. The open resource work must not silently enlarge this exception.

### Conditions for an acceptable maintained patch

| Responsibility | Required policy before selection |
| --- | --- |
| Auditability | Retain rationale and reachability classification beside a reviewable patch. Verify ordinary exceptions, both stop mechanisms, all caller propagation, cleanup and fresh-runtime health. Keep excluded features explicit. `Promise.try` test overcoverage does not expand the ES2023 profile. |
| Rebase and silent divergence | Every upstream change requires reviewing new/changed Promise/async and exception sites, not just a clean apply. Rerun the complete matrix and native sanitizers; fail on source-hash/anchor mismatch. Re-audit excluded routes if language/profile changes. |
| Supply chain | Pin upstream commit plus patch digest and binding revision; retain upstream/license provenance and reproducible acquisition instructions. Build exactly one patched engine matched to the binding headers/layout. Avoid accidentally linking a second unpatched rquickjs-sys engine. |
| Reproducible builds | Record toolchain, target, flags, patch order and generated bindings; verify clean/offline-capable source acquisition and deterministic patch application. Byte-for-byte binary reproducibility is a separate check, not implied by a source hash. |
| Platform builds | Guards do not intentionally introduce platform APIs, but C/compiler behavior, stack margins and binding linkage need target builds and execution. Preserve sanitizer coverage where supported and equivalent target checks elsewhere. |
| Security response | Identify an accountable owner/reviewer and update procedure. Pinning one known-good revision plus patch set is reasonable for a release; permanently freezing it to avoid rebases is not. Track advisories and upstream fixes, including fixes without CVE labels. |
| Upstreaming and exit | Prefer an upstream report/patch with the reduced regression corpus before production adoption. Acceptance would reduce carry but must not be assumed. Remove local changes only after equivalence testing. This review sends nothing upstream and authorizes no maintained fork. |

The burden is acceptable for continued evidence gathering and potentially selection with these conditions. No measured staffing capacity or long-term update performance exists yet. Explicit maintainer acceptance is a selection input, not something a documentation recommendation can manufacture.

## Permanent RegExp admission cost

This is a reasonable **but substantial** runtime policy layer for finite data processing under RFC §10. It is more than a length check. The [route probe](../../experiments/quickjs-regexp-admission-spike/README.md) and [implementation](../../experiments/quickjs-regexp-admission-impl-spike/README.md) establish the necessary boundary:

- Measure literal patterns in every unchanged module before QuickJS compilation, and before a secondary parser's potentially expensive RegExp validation. Fail closed on parser disagreement.
- Privately capture the native constructor, replace constructor/prototype recovery routes, and prevent access through retained aliases, subclasses, species and generic receivers.
- Cover dynamic construction, `RegExp.prototype.compile`, generic `@@split`/`@@matchAll`, and String `match`/`matchAll`/`search`. Distinguish operations that do not compile; rejecting all string operations would change allowed behavior.
- Preserve single coercion and ES2023 observable access order. Genuine admitted RegExp clones need internal-source readmission, since escaped `.source` can be longer than the original pattern. Generic-operation wrappers and changed native fast paths require semantic and performance review.
- Latch deadline/cancellation/resource refusal before compilation; use the patched propagation path for Promise/async callers. Matching still relies on engine interruption and finite input/resource policy.

The existing 30-route matrix, reachability checks and literal graph tests are a useful upgrade oracle. The candidate bound produced worst observed local debug compilation around 81–86 ms; matching gaps reached about 43 ms. Neither is a portable ceiling. Admission also cannot guarantee immunity to a future compiler complexity bug for a short pattern. Release builds and slower target hardware need conservative policy and adversarial calibration, including subject-length terms.

New syntax/flags, constructor semantics, species behavior, String methods or native compiler call sites can add compilation paths. Every engine update therefore needs a native compile-entry/route audit even when the RFC stays ES2023. A future language-baseline expansion requires an explicit new audit and tests; unknown paths must not be exposed accidentally. The current `v` acceptance and incomplete edition gate are pre-selection gaps. The invariant is portable; this facade and its preserved generic semantics are engine-specific maintenance.

The policy is acceptable because scope can be closed and tested without editing the RegExp compiler. It becomes disproportionate if maintaining standard observable behavior repeatedly requires new algorithm emulation or native patches. That is a reconsideration trigger, not permission to keep extending the workaround indefinitely.

## Alternative engines and containment strategies

### JavaScriptCore

Apple supplies the [JavaScriptCore framework](https://developer.apple.com/documentation/javascriptcore) on macOS, iOS, iPadOS and tvOS. System JSC avoids shipping an engine binary on those platforms and benefits from OS security servicing, but behavior/version availability follows the supported OS matrix. ES2023 adequacy and removal of newer/host extensions must be tested per minimum OS; framework availability alone is insufficient.

The important distinction is **public system framework versus custom WebKit/JSC build**. `JSContextGroupSetExecutionTimeLimit` and `JSGlobalContextSetEvalEnabled` appear in WebKit's [private API header](https://github.com/WebKit/WebKit/blob/c4c7d4d56e3e663789bbcff34edd163b45eed345/Source/JavaScriptCore/API/JSContextRefPrivate.h), not its public context contract. Availability annotations do not make private calls suitable for an ordinary App Store app. The time-limit callback is a useful watchdog for a custom embedding, but not evidence of a public Apple-platform cancellation contract covering all native work.

The [public context API](https://github.com/WebKit/WebKit/blob/c4c7d4d56e3e663789bbcff34edd163b45eed345/Source/JavaScriptCore/API/JSContextRef.h) does not establish the required per-invocation heap quota, single-job terminal checkpoint, or pre-evaluation module capture. Public value/property APIs alone have not proven positive ordinary-class identification and trap/getter-free §6 extraction. Custom loaders and private/internal hooks may address gaps, at the cost of becoming a different embedding. Restricted-global construction is plausible without WebView host objects, but intrinsic extension removal and every function-family dynamic compiler must be re-proven.

Linux has WebKit/JSC ports; Android and Windows distribution still require choosing and maintaining an appropriate custom build/binding path, rather than linking Apple's framework. The prior evaluation's `rust_jsc` route used a Kedo fork and Linux/macOS build assumptions; it is not proof of one Android/Windows/Apple-mobile solution. [WebKit licensing](https://webkit.org/licensing-webkit/) includes BSD and LGPL components; distribution obligations require checking the exact selected build, not assigning one blanket license to every JSC configuration.

Conclusion: attractive Apple-first distribution, insufficient public control evidence for this RFC, and substantial non-Apple/custom-build burden. Using system JSC on Apple and another engine elsewhere would multiply semantic qualification and undermine the desired common core. No current evidence justifies that pivot.

### V8

V8 offers meaningful advantages: public isolate boundaries, cross-thread `TerminateExecution`, termination state distinct from normal exceptions, code-generation control, module instantiation/evaluation APIs, native type/descriptor inspection, heap constraints and near-limit callbacks. These are real control primitives, not a guarantee of whole-process memory containment or immediate cancellation inside arbitrary embedder callbacks. Heap limits omit other allocations; an unrecovered OOM can be fatal. Termination, reentry and disposal ordering still need a trusted host protocol. See the [isolate API](https://v8.github.io/api/head/classv8_1_1Isolate.html).

The serious semantic uncertainty is RFC completion timing. V8's [microtask queue](https://v8.github.io/api/head/classv8_1_1MicrotaskQueue.html) and inspected [Rust binding](https://github.com/denoland/rusty_v8/blob/2f588046bf45a7b9adeda3ed0f0e881d38e6f3f5/src/microtask.rs) expose checkpoints that drain the queue, not the demonstrated QuickJS one-job pump. Promise hooks/state inspection are promising but do not by themselves establish stopping after the current complete job when the operation settles and before the next unrelated job. Terminating at the instant of settlement may incorrectly interrupt the current job. This is an unresolved fit question, not a proven V8 impossibility.

Snapshots could amortize trusted bootstrap, but only pristine setup can be shared; they cannot share invocation state or settle terminal-boundary semantics. They also add version/target/build artifacts. Modern V8 implements beyond ES2023, so parser/profile gating and restricted-global audits remain necessary. Modules, value conversion and native RegExp/GC interruption must be re-proven against the same oracles.

Current [rusty_v8 build documentation](https://github.com/denoland/rusty_v8/blob/2f588046bf45a7b9adeda3ed0f0e881d38e6f3f5/README.md) describes prebuilt static archives or GN/Ninja/Clang source builds, Android arm64/x64 builds, and iOS device builds using JITless execution with WebAssembly disabled. Thus “V8 cannot run on iOS” is not an adequate rejection. [JITless V8](https://v8.dev/blog/jitless) supplies an execution mechanism; it does not establish App Store distribution or tvOS support. Desktop/Android are credible paths. Apple device signing, minimum OS, tvOS toolchain and distribution remain unproven here.

V8's larger build/distribution system, rapid binding/engine updates and artifacts are meaningful costs for this small Rust project. No comparable stripped-binary or startup measurement exists here, so no invented MB or latency figures decide the result. BSD-style engine and MIT binding licensing are manageable with dependency notices. V8's mature debugging ecosystem and public termination API are advantages; neither closes the job-control question. It is the strongest fallback, not presently a demonstrated improvement.

### Boa and the previously considered Bellard engine

The [Boa investigation](2026-09-28-boa-reaction-ownership.md) must not be restarted or misrepresented. Under the old persistent-realm proposal, registration ownership and pre-effect suppression of missing-handler/species reactions needed deeper engine integration than the current QuickJS guard patch. Callback tokens and public job hooks did not solve it.

**Model B removed selective cross-invocation reaction revocation from the requirements.** The old blocker therefore does not disqualify Boa under the current RFC. Its Rust implementation, native integration and AST are useful advantages. However, fresh-context whole-graph/GC retirement, exactly controlled jobs, hard Promise/async termination, native-work budgets, module capture and full value transfer have not received equivalent proof. Rust implementation does not automatically establish deterministic termination or resource limits. Boa AST's empty-attribute loss remains concrete, independently addressed by the Oxc experiment. Existing evidence provides no reason to trade the bounded QuickJS fix for this larger unproven set.

Bellard QuickJS was in the initial evaluation. It shares relevant architecture and the historical stop-swallow report, while the reviewed public class/Proxy inspection surface was less convenient. It offers no demonstrated escape from these problems. No broad new engine search is warranted; Hermes and other engines are not added merely to enlarge the comparison.

## Apple containment correction

The historical process review's blanket statement that ordinary iOS/iPadOS/tvOS apps cannot have helper processes is **too broad**. Preserve that review as dated evidence; use the following corrected conclusion for future decisions.

| Mechanism | Authoritative evidence and project applicability |
| --- | --- |
| Arbitrary `fork`/`exec` or desktop helper executable | Do not assume an ordinary mobile app has the desktop process-spawning contract. This review establishes no such route. That restriction does not imply an absence of system-managed extension processes. |
| Custom ExtensionFoundation app extensions | Apple explicitly documents application-defined extension points, isolated risky computation, bundled non-UI extensions and host-defined XPC interfaces. This is a credible general computation mechanism, not inherently browser-only. [Adding extension support](https://developer.apple.com/documentation/extensionfoundation/adding-support-for-app-extensions-to-your-app). |
| Process availability | [AppExtensionProcess](https://developer.apple.com/documentation/extensionfoundation/appextensionprocess) lists iOS/iPadOS/tvOS 26, macOS 13 and other platforms. Programmatic extension-point generation is documented from OS 26. Older mobile/TV deployment targets are not covered by these availability facts. No project OS floor is selected here. |
| Connection and retirement | The system can reuse an existing process. [invalidate](https://developer.apple.com/documentation/extensionfoundation/appextensionprocess/invalidate%28%29) terminates it when the invalidated object represents the last connection. Multiple connections can keep it alive. No numeric termination deadline or complete RFC quiescence protocol is documented by that API. |
| Enhanced-security helper extensions | Apple's [helper guide](https://developer.apple.com/documentation/xcode/creating-enhanced-security-helper-extensions) specifically supports isolating untrusted computation on iOS/iPadOS/macOS. Its [security guide](https://developer.apple.com/documentation/xcode/enabling-enhanced-security-for-your-app) describes related build settings/entitlements and additional platforms. Neither establishes enhanced-helper support on tvOS; general tvOS ExtensionFoundation availability must not be conflated with that hardened configuration. |
| Conventional system extension points | Purpose-specific share/action/etc. extensions are not arbitrary persistent JS workers. Their lifecycle constraints do not negate newer application-defined extension points. [Building a host-app extension](https://developer.apple.com/documentation/extensionfoundation/building-an-app-extension-to-support-a-host-app) provides the relevant bundled-extension model. |
| BrowserEngineKit | [BrowserEngineKit](https://developer.apple.com/documentation/browserenginekit) is a browser-engine architecture with regional/entitlement conditions, not a generic JS worker entitlement. Apple's [browser extension guide](https://developer.apple.com/documentation/browserenginekit/creating-browser-extensions-in-xcode) says embedded alternative browsers in non-browser apps cannot use browser extensions or JIT; browser-only entitlements cannot be repurposed for an ordinary media app. It is unsuitable as this project's general containment foundation. |

**Conclusion:** system-managed containment is technically and publicly supported for general application extension work on relevant modern Apple OS versions; it is a credible optional architecture for an ordinary media/player app. Its suitability as Universal Source's mandatory hard-termination domain is **unresolved**, constrained by OS availability, signing/sandbox configuration and demonstrated lifecycle behavior. It is not categorically prohibited, nor proven deployable for all charter targets.

A future containment proof would need sole process/connection ownership, behavior while native code spins, observed termination before terminal publication, late-XPC rejection, fresh-runtime recreation even when the system reuses a process, and no source-visible cleanup. Parent cancellation cannot count as completion while source effects remain possible. Extension suspension/background limits and target-specific memory policy also matter. No such platform code or IPC was built here. Apple's [review guidelines](https://developer.apple.com/app-store/review/guidelines/) remain a separate distribution constraint on public API use and downloaded functionality; API existence is not a product approval prediction.

Desktop workers and Android [isolated services](https://developer.android.com/guide/topics/manifest/service-element#isolated) also remain plausible containment mechanisms rather than completed project proofs. OS kill/reap and revocation can enforce abandonment, but do not supply hard-real-time guarantees or make a wrong in-process terminal checkpoint correct. This correction strengthens the optional containment strategy; it does not by itself favor switching engines or requiring IPC everywhere.

## Security and isolation posture

| Strategy | What it buys | Residual responsibilities |
| --- | --- | --- |
| Patched QuickJS in-process | Fresh Runtime/Context, exact restricted surface, explicit capabilities, non-executing transfer, finite admission, patched stops and heap/stack settings form a relatively inspectable execution boundary. | C memory corruption remains in the app's process. All bridge/allocator/native latency and profile assumptions matter. Fresh realms do not defend against arbitrary engine memory-safety bugs. |
| Patched QuickJS plus outer process/extension | Adds address-space and OS-sandbox defense in depth, independent worker abandonment and possibly OS resource controls. Preserve the same inner semantics. | IPC validation, process ownership, quiescence, signing, platform availability and parent-side authority checks add substantial work. Sandbox policy must actually restrict authority. |
| Unpatched QuickJS with outer containment only | Parent can ultimately terminate a stuck worker where supported. | Does not automatically prevent source continuation after a swallowed stop before the kill, unauthorized side effects, or wrong terminal ordering. Gate all authority in the parent and prove worker quiescence. Cannot simply relabel the upstream engine correct. |
| Alternative engine in-process | V8 has strong termination/isolate APIs; JSC can exploit system servicing; Boa reduces some native-language risks. | Each still needs the profile, whole-graph lifetime, native-work bounds, value boundary and authority proof. An isolate/context is not an OS security boundary. |

QuickJS's smaller accessible implementation and existing source-level evidence make this particular profile easier to audit than starting from a larger unaudited integration. That is an audit-cost judgment, not evidence that a smaller engine has fewer vulnerabilities. Larger projects may have stronger security investment and tooling. Engine size alone decides neither safety nor fit.

| Interrupt/termination semantics, allocator/stack limits, leak-free root/job/runtime destruction | Engine-specific; re-prove from scratch | Neither QuickJS sanitizer results nor its runtime-drop proof qualify another engine. |
| Platform build/release evidence | Engine-specific; re-prove from scratch | Current QuickJS evidence is itself incomplete. A switch does not discard a platform proof that never existed. |

A serious switch likely requires **six to eight coherent evidence units**, not reauthoring every review: (1) lifecycle/job terminal boundary, (2) hard-stop propagation, (3) module capture/loading, (4) hardening/dynamic code, (5) value transfer, (6) native CPU/memory/stack/RegExp behavior, (7) compiler/preflight agreement, (8) platform/build qualification. Closely related units might combine after initial results. This is a scope estimate, not a staffing or elapsed-time forecast. The existing review chain makes those units better specified; they do not turn them into already passing alternative-engine tests.

Past effort alone is not a retention argument. Reusable oracles lower switching risk, and switching is appropriate if a remaining QuickJS gate requires disproportionate engine maintenance. At present the prospective cost and semantic uncertainty of alternatives exceed the identified QuickJS patch/policy burden.

## Gates before selection versus implementation work

### Must complete before an engine-selection ADR

1. **Integrated resource/failure closure.** Demonstrate the actual hardened patched configuration with admission, §6 transfer and lifecycle retirement together. Bound and classify engine/host allocations, native-work intervals and stack failures without source-controlled error parsing. Show trusted stops survive every Promise/async path; ordinary unclassified stack errors may remain SOURCE_ERROR as RFC permits. Identify any extra engine modification as a new decision, not an extension authorized here.
2. **Complete module/path containment feasibility.** Prove the selected resolver design on hostile path/graph fixtures, stable exact bytes, private module denial and capture-before-evaluation. This review implements none of it. A limited non-production proof is enough; a production package loader is not required before selection.
3. **Final parser/preflight strategy.** Establish a coherent ES2023/early-error/import-attribute/literal-admission approach, including dynamic RegExp flags, bounded parsing and fail-closed agreement. Demonstrate that all sites excluded from the async patch really are unreachable. Parser feasibility can be decided independently; no parser is chosen here.
4. **Cross-platform and Apple embedding feasibility.** Build/link the same binding+engine+patch arrangement for Linux, Windows, Android, macOS, iOS/iPadOS and tvOS; execute representative lifecycle/stop/FFI/resource cases on available representative targets. Apple public-API, signing and no-JIT device feasibility must be evidenced. A simulator/compile-only result must be labeled and cannot alone close device behavior. Document minimum toolchains/OS and any unavailable verification rather than claiming charter-wide readiness. A full media application or optional extension IPC implementation is unnecessary.
5. **Patch ownership/integration/upstream strategy.** Establish the single-engine reproducible build route, source/patch provenance, accountable maintenance, upgrade/security regression gate and upstream engagement plan. No upstream acceptance is assumed. User/project approval of this obligation belongs in the eventual selection decision.

These are finite questions, but their answers can still falsify Outcome A. In particular, unbounded native work inside the admitted profile, unrecoverable routine memory exhaustion, an uncontainable import path, unavailable mobile build/control APIs, or a second substantial engine subsystem patch would require reevaluation. “Finite” does not mean already cheap or scheduled.

### Can follow selection during production implementation

Production Rust API factoring, host-service signatures and implementations, complete JS conformance execution/reporting, performance tuning and policy calibration across the supported fleet, packaging/CI polish, developer diagnostics and optional outer containment integration can follow selection. Representative resource/platform feasibility precedes selection; exhaustive platform regression and release certification follow it. RFC acceptance remains a separate explicit contract action, never inferred from an engine ADR. Existing U1/U2/P1/D1/D2 issues keep their recorded dispositions.

## Exact next task

Run one **non-production QuickJS integrated resource/failure closure spike** on the existing pinned revision plus the already demonstrated experiment-local patch. Reuse the current hardening, admission, value copier and lifecycle corpus; do not introduce a production runtime or change engine pins. It must actually invoke the global hardener and demonstrate a single correctly linked patched engine through the Rust binding.

The discriminating question is: **can the existing narrow patch and admission policy compose with trusted allocation/stack/native-work failure handling and RFC retirement, without another substantive engine change?** Exercise initialization, direct calls and pumped jobs; ordinary exceptions versus latched cancellation/deadline/admission/allocation failures; boundary enumeration/string allocations; pathological admitted regex and matching subject sizes; no post-stop continuation, late delivery or final drain; and healthy independent runtimes. Preserve ordinary stack-error classification unless a trusted host limit supplies a reason. Report any residual non-polling native work and the finite host policy that bounds it, rather than inventing an exact RSS or real-time promise.

A pass closes gate 1 only. Then close gates 2–5 before proposing the engine ADR; this review does not package every remaining Phase 3 task into that spike. A failure requiring broad new engine surgery should reopen this recommendation. If a switch becomes necessary, the smallest fallback is **one V8 fresh-isolate Promise terminal-boundary and hard-termination spike** using the existing lifecycle/async corpus: prove the current job finishes, the next unrelated queued job does not run, and uncatchable cancellation reaches the host. It is a contingency, not a second task authorized or required by Outcome A.

Outcome B is unnecessary today because no alternate has shown a concrete overall advantage that requires an immediate head-to-head spike. Outcome C is unsupported by a demonstrated superior cross-platform path. Outcome D is premature given the five gates. Outcome A means continue bounded evidence work, not authorize engine maintenance or production integration by implication.
