# Phase 2 closure review — 2026-09-28

Status: **Phase 2 closure accepted.** All four exit criteria are met for the bounded static declarative reference runtime. No normative contradiction or blocking static-profile evidence gap was found. ## Host API, boundedness and evidence limits

The [Host API](../../spec/host-api.md) requires requested/effective authority separation, parsed normalized exact origins and rejection on each use. `EffectiveGrants` cannot add requested authority; dispatch checks both requests and grants, including a grants object from another source. Tests cover default denial, changing grants between calls, DNS/IPv6/default/non-default ports, semantic duplicates and forbidden components, different schemes/subdomains, and denied posters/media. Unreturned data does not require authority. P1 remains unchanged.

A static source cannot call any of the eight executable host services: its required-service list is empty and it evaluates no code. Consequently no cookie jar, persistent store, HTTP client, HTML parser, crypto/keychain access, logging service or JavaScript globals are exposed. The Rust JSON and URL validation libraries are internal implementation details, not portable service bindings. Service availability diagnostics, signatures/encodings, cookie/storage namespaces, retention, concurrency and quotas must be implemented and tested when those services exist; omission here does not permit silent no-ops later.

Returning a URL is not network access. Every future consumer must recheck current grants at actual use and every redirect, including media-subsystem requests, refuse access if it cannot enforce the boundary, preserve header-origin restrictions, and enforce cookie rules. Any stricter DNS/destination policy must also apply after resolution/redirects. Those obligations are documented and **outside this static runtime's exit criteria**. No HTTP/DNS/redirect/player implementation is needed for closure, and these tests provide no consumer-conformance evidence. Hosts must supply current grants, cancel/dispose outstanding calls when revoking their authority as needed, and never treat snapshot inspection as permission approval.

### Memory, response and execution limits

The [runtime policy](../../runtime/README.md#lifecycle-and-invocation-policy) matches the code: default/hard load ceilings are 65,536 manifest bytes, 8,388,608 entry bytes, 8,454,144 combined consumed bytes and 64 container levels. Default invocation limits are 5 seconds (configurable to at most 60), 65,536 compact input bytes, 8,389,632 compact result-envelope bytes, 64 input levels and 64 active-plus-waiting calls. Byte/admission caps can only be lowered. Fixed fallback diagnostics below 128 bytes are exempt from a smaller result cap so failure remains reportable. Boundary, over-limit, invalid-configuration, escaped-byte and queue-cap tests exercise these policies.

The memory obligation is satisfied **structurally for this static execution model**, not by precise allocator accounting. The loader consumes bounded bytes/depth; parsed values, reference sets and origin lists derive from that finite data. One call per instance constructs/validates a selected result copied from the immutable bounded snapshot. Copies and validation sets can coexist but cannot grow through source loops or persistent mutation. Paged metadata is fixed in shape. Invocation input is borrowed, traversed with depth and interruption checks, then measured into a counting sink; it is not copied into an unbounded runtime queue. Admitted-call metadata is capped. No concrete unbounded runtime-owned execution-memory path was found.

A lower result cap does not prevent the temporary construction of a larger selected result; that allocation remains bounded by the load ceiling plus representation/container overhead. This is not an exact heap/RSS quota or an OOM guarantee. Caller-owned inputs, retained returned values, threads, the total number of instances and process-wide budgets remain the embedding host's responsibility. Bounded input does not prove maximum observed memory usage across all allocators. No persistent-storage quota is relevant until storage exists. These limitations do not warrant an unused allocator/service abstraction merely to close Phase 2.

Cancellation is cooperative. Cloning, shape validation and URL parsing can finish their current finite stage before the next checkpoint; cancellation does not preempt a Rust instruction. Input traversal/counting and returned-origin iteration check interruption, and publication rechecks deadline/cancellation under locks. After observation no further stage starts, and no late result or worker survives the synchronous call. Queue polling is at most 10 ms while scheduled, not a hard scheduling guarantee. Disposal waits for quiescence. This meets the static contract without arbitrary executable loops, network work or side effects; it must be reassessed for JavaScript. A finite acceptance deadline does not promise hard real-time response latency.

Filesystem containment assumes the host controls a stable root and ancestors during loading. Canonicalize/open does not withstand a concurrent hostile writer. Tests prove static path/symlink containment locally, not Windows reparse-point behavior or all OS semantics. Blocking filesystem I/O, process scheduling, abort-mode panics and allocation aborts are outside the library's recovery guarantee. Its own returned errors are fixed/redacted; the embedding host remains responsible for its process-wide panic hook and diagnostics.

### Production-path evidence

The [harness](../../runtime/tests/declarative_conformance.rs) loads the real minimal example or empty-home context afresh, constructs checked grants, creates `Instance`, and invokes its production public boundary. All 34 authored cases pass unchanged. Schema/count/ID checks and independent envelope/structural comparison run in the harness; setup failure cannot masquerade as a Source API expected error. The tested [comparison helper](../../runtime/tests/support/mod.rs) preserves array order, missing/null and numeric distinctions without lossy large-integer equality. Python structural validation remains separate from execution.

Lifecycle tests use private `cfg(test)` gates and clock control inside the same `invoke_inner` reached by public `invoke`. They retain admission, serialization, budgets, dispatch, grants, result checking and terminal publication; they do not substitute a mock lifecycle. Public-wrapper tests and a real-clock queue deadline complement controlled schedules. Independent-instance tests demonstrate progress while another instance is held, owned result independence and disposal isolation. Internal malformed-result and injected-panic tests establish defensive behavior, not new portable fixture expectations.

Evidence is local Darwin arm64 with Rust/Cargo 1.96.0. It does not establish Android/Apple embedding, Windows/Linux behavior, a native ABI, independent-runtime agreement, real-site/CDN interoperability, exhaustive security verification or a universal URL profile.
