# QuickJS fresh-realm lifecycle feasibility

**Outcome A — lifecycle viable.** The examined public QuickJS-NG/rquickjs APIs suffice for the Model B lifetime, job-boundary, retirement, native completion and non-executing extraction primitives demonstrated by this spike. There is no unresolved blocker in those demonstrated lifecycle mechanisms. This conclusion does **not** select QuickJS-NG, accept RFC 0001, implement JavaScript execution or establish full binding/engine conformance.

Baseline: `01154b767b74afa5a0a8dd2d248c6a145ea37890`. The [lifecycle decision](2026-09-28-javascript-lifecycle-decision.md) and [proposed RFC](../../spec/rfcs/0001-javascript-execution-binding.md) are unchanged. Phase 3 remains active. Only the [isolated experiment](../../experiments/quickjs-lifecycle-spike/README.md) and supporting documentation were added; previous counterexamples remain valid against persistent-realm designs.

## Experiment architecture and ownership

A realm is implemented by **one dedicated Runtime plus Context per validation/executing invocation**. Sharing one runtime between calls is deliberately not the tested strategy. The host runs an invocation in `Context::with`, retains scoped JavaScript handles on that owner thread, and explicitly pumps one job at a time only while allowed. No futures integration, Tokio, automatic event loop or hidden final drain is enabled.

The minimal `Delivery` helper owns a resolver only while its generation is active. External completion messages contain a host generation and owned integer, never Function/Promise/Value/Context/Runtime. Revocation closes the gate and removes the resolver before realm retirement. A mismatched/closed token is rejected before any JS API call. Generation identity must never be reused while an old event can arrive; the experiment uses distinct fixed generations 1 and 2. A native callback captures only host counters and a drop sentinel, never a rooted JS value or runtime, avoiding a host/JS ownership cycle.

Retirement order is: stop pumping and delivery; revoke scope; inspect/copy or classify the candidate without executing source; release scoped/Persistent values, modules, resolvers and callback roots; drop all Context and Runtime owners; verify `WeakRuntime::try_ref()` fails and native drop counters advance; check host interruption before publishing host-owned data. Destruction is not reported from merely dropping a Context handle. Error/JobException objects can themselves retain context state and must be released too.

| Handle | Lifetime rule established |
| --- | --- |
| Value, Function, Promise, module, Ctx | Scoped values cannot escape `with` directly (compile-fail test). Keeping a scoped handle during a pending invocation is allowed. All such handles must be dropped before final runtime teardown. |
| Persistent/root | Can outlive a Context handle and restore into another context of the same live runtime. This preserves the old closure/realm, so it is forbidden across Model B calls. No invalidation is supplied automatically by Rust typing. Release every clone before dropping Runtime. |
| Context/Runtime clone | Keeps the runtime owner alive; even without clones, runtime-wide queued work survives dropping a Context. Never cache these across execution realms. |
| WeakRuntime | Does not keep the runtime alive; used only to observe retirement, not to revive a finished invocation. |
| Host callback | Native destructor releases test-only host state during GC/teardown. It must not reenter JS or retain JS ownership cycles. Callback liveness is separate from its permission token. |
| External event | Plain host data may outlive both context and runtime and cross a Rust thread. It cannot call an old resolver because no resolver is carried and the owner registry is revoked/empty. |

No root is intentionally allowed to outlive the actual runtime, and no invalid cross-runtime raw value is constructed. Public Persistent restoration rejects an unrelated runtime safely, but same-runtime cross-context transfer is allowed: the Rust API is not an invocation-isolation policy. This is why the dedicated runtime and no-escaping-roots discipline are necessary embedding choices already allowed by RFC §10, not a new source restriction.

## Non-executing extraction boundary

Generic JavaScript serialization is unsuitable: property get, coercion, toJSON and Proxy enumeration can execute arbitrary code. The RFC already excludes Proxy/accessor/exotic/native objects and accepts only primitives and restricted ordinary records/dense arrays; no new representational restriction is needed to avoid executing those hooks.

The probe samples ordinary object/array class IDs through public `JS_GetClassID`, rather than hard-coding private IDs. It captures trusted prototypes before user code, rejects Proxy first, rejects all other engine classes even if source changed their prototype, then enumerates all own string/symbol keys and calls public `JS_GetOwnProperty`. This obtains accessor functions as values for rejection without invoking them. Descriptor values/getters/setters and atoms have balanced lifetime management. For accepted records/arrays, inspection does not traverse inherited getters, invoke a thenable or call toJSON. A class-created ordinary object reset to an allowed prototype follows the RFC's structural rule; construction history is not inferred.

This demonstrates a non-executing copying path, **not a complete converter**. The test helper uses depth 8, 128 visited values and 1024-byte individual strings; engine memory limits bound enumeration allocations in these probes. Comprehensive UTF-16/surrogate handling, total expanded byte accounting, all native/helper brands, large-object limits and actual operation-envelope schemas still need their own production/conformance work. The helper must not be promoted unchanged. No FFI safety guarantee is inferred from a test passing: the public-call ownership contracts and ordinary-class preconditions are reviewed explicitly, with no private internals or invalid references.

## Initialization, termination and threading limits

Fixed modules are declared/evaluated synchronously; their evaluation Promise is directly observed as resolved/rejected, without `finish()` pumping. Each fresh runtime gets a new module environment even with the same module name/text. A successful load-validation domain and a call domain can therefore use the same immutable bytes while sharing no JavaScript objects. Initialization is module evaluation/setup only, never a source-visible init export.

The experiment obtains fixed exports **after evaluation** to exercise invocation/state. It does not claim this satisfies RFC §2's capture-before-evaluation rule; complete module capture/replacement enforcement is explicitly excluded from this lifecycle unit and remains the next engine-selection evidence gap. Module compile/link/instantiation APIs must be reviewed separately before a binding can be selected/implemented. There is no silent alternate capture rule or RFC amendment here.

Setup resource failure can remain a host-facing loading diagnostic or a ready-call resource failure depending on host phase. Ordinary source initialization failure during an already admitted call can be classified SOURCE_ERROR and followed by a new realm without reusing the failed one. No engine API forces changing that mapping. Current cancellation/timeout/resource policy discards both execution domain and logical instance; normal/source-failure completion retires just the domain. Deadlines are checked again after host-only copying and cleanup; detached I/O is never awaited during teardown. No process-abort recovery, exact heap/RSS quota, interruption latency or hard real-time claim follows. Earlier regexp-hook evidence remains unchanged; native-work coverage is not expanded here.

Pinned features leave Runtime and Context non-Send/non-Sync, using same-thread ownership and a runtime borrow gate. Execute/pump/copy/drop on the owner thread; external workers send ordinary data only. `Context::with` holds the runtime gate: use Ctx's single-job API inside it, not Runtime methods that would borrow the same gate again. The explicit runtime pump appears only outside `with` in the negative control. `parallel`/futures features offer different integration policies but are disabled and untested; no claim that their scheduling/destruction obeys this boundary. Native callbacks must avoid JS-root cycles and source reentry from destructors. Every persistent clone, error handle, module, resolver and context owner needs a defined release path.

## Conclusion and next evidence gap

**Outcome A applies to the demonstrated lifecycle primitives**, with the concrete embedding discipline above. No new source semantics, private engine extension, patch, Promise cancellation operation or extra source restriction is required. It removes the lifecycle-specific blocker for this candidate approach; dropping Context alone and opportunistic runtime reuse would still be nonconforming. Complete embedding implementation, all conversion cases and cross-platform disposal are not claimed by this local experiment.

Next task: **a narrowly scoped module instantiation/export-capture feasibility review and minimal proof** for RFC §2 through these pinned public APIs. Establish whether directly declared operation functions can be captured before any module evaluation and checked after evaluation without weakening the fixed export rule; if not, record that specific blocker. Do not implement the production loader, reopen the lifecycle decision, select an engine or start production JavaScript execution. Global hardening, full sandbox/resource/platform/distribution/performance/conformance evaluation remain separate engine-selection dimensions.

Full validation and delivery scope are in the [completed plan](../plans/completed/2026-09-28-quickjs-lifecycle-spike.md). Production runtime/tests/dependencies, prior experiments, normative contracts, RFC status and ADRs remain unchanged. No push, tag or release.
